# فهدان للعود | FAHDAN OUD

**الإصدار 0.1.0 — الهيكل البرمجي الأساسي**

مشروع متجر إلكتروني عربي بـ **React + TypeScript + Vite** للواجهة، و**Node.js + Express + TypeScript** للـ API، و**PostgreSQL + Prisma** للبيانات. يحتفظ بالهوية المعتمدة: أخضر داكن `#172721`، ذهبي `#BA9764`، خلفية عاجية `#F7F4EE`.

> **ليس متجرًا جاهزًا لاستقبال الطلبات**: الدفع والشحن وإنشاء الطلبات محجوبة عمدًا. الأمثلة والأسعار التوضيحية ليست منتجات حقيقية. يجب أن تُعتمد معلومات التواصل وقصة العلامة والسياسات قبل النشر.

## معاينة فورية دون تشغيل الخادم

افتح الملف `preview/index.html` في المتصفح لمراجعة الشكل المبدئي المعتمد. هذه نسخة HTML توضيحية مستقلة؛ النظام الجديد يعمل عبر `apps/web` و `apps/api`.

## 1. المتطلبات

- Node.js **20.19+** (يُفضّل الإصدار 22 LTS).
- npm، وPostgreSQL 16 (مباشرة أو عبر Docker Desktop).
- اتصال بالإنترنت لتنزيل حزم npm أول مرة.

## 2. التشغيل المحلي — Windows PowerShell

```powershell
# من داخل مجلد fahdan-oud-app
npm install
Copy-Item apps/api/.env.example apps/api/.env
# افتح apps/api/.env وعدّل JWT_SECRET و ADMIN_EMAIL و ADMIN_PASSWORD
# استخدام Docker Desktop لتشغيل قاعدة البيانات المحلية:
docker compose up -d
npm run db:generate
npm run db:push
npm run db:seed
npm run dev
```

- واجهة المتجر: **http://localhost:5173**
- API: **http://localhost:4000/api/v1/health**
- دخول المالك: **http://localhost:5173/admin** (بعد تعيين بياناته في `.env` وتشغيل `db:seed`).
- إن أردت رؤية منتجات وهمية من قاعدة البيانات نفسها: غيّر `SEED_DEMO=true` مؤقتًا في `apps/api/.env` وأعد تشغيل `npm run db:seed`، ثم ارجعه إلى `false`. لا تُستخدم هذه الخطوة في الإنتاج.

**إن لم تكن لديك Docker:** وفّر قاعدة PostgreSQL مستقلة وعدّل `DATABASE_URL` ثم تابع `db:generate` و `db:push` و `db:seed` و `dev`.

**توليد سر JWT من PowerShell:**

```powershell
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

ضع الناتج في `JWT_SECRET` بدل القيمة التوضيحية. اختر كلمة مرور فريدة بطول 16 رمزًا على الأقل لحساب المالك. لا ترفع `.env` إلى أي مستودع Git.

## 4. قواعد المخزون

- كل صنف عود يملك رصيدًا في **وحدته الأساسية بالجرام**. المتغيرات (10، 20، 28، 36، 50، 100، 125، 250، 500، 1000) ليست مخزونًا مستقلاً.
- العطور قد تستخدم **ملليلتر**، والبكجات **قطعة**. لا يُفرض الجرام على جميع أنواع المنتجات.
- المتاح = الكمية الفعلية - المحجوزة. لا يتم تقليل مخزون على أساس تجربة السلة.
- تكلفة الشراء، المورد، وحدات تكلفة الدفعات وCOGS موجودة في نماذج خاصة بالخلفية، ولا تصل لواجهة العميل.
- في الإنتاج، البيع الحقيقي يحتاج معاملات ذرية وحجزًا مع انتهاء صلاحية وتأكيدًا للدفع قبل الخصم النهائي.

## 5. حالة التحقق

- أُنشئت ملفات المصدر والبنية التقنية وقيم التجربة.
- لم يُجرَ `npm install` أو build كامل داخل بيئة الإنشاء بسبب عدم إمكانية الوصول إلى registry.npmjs.org؛ يلزم التثبيت واختبار التشغيل في جهاز يتصل بالإنترنت.
- راجع `docs/ROADMAP.md` لما أُنجز وللخطوات التالية، و`docs/SECURITY-NOTES.md` لما يلزم قبل التشغيل التجاري.

## 6. النشر لاحقًا

يمكن فصل `apps/web` و`apps/api` إلى خدمات مع PostgreSQL، وربطهما باستضافة تدعم Node وPostgreSQL مثل Railway عند طلب النشر. يجب ضبط `WEB_ORIGIN` و`VITE_API_BASE` وأسرار الإنتاج، وتشغيل `prisma migrate deploy` بعد إعداد migrations، وعدم نشر أي معلومات وهمية على أنها بضائع للبيع.

## 7. نشر موحّد في Railway

- خادم Express يستضيف واجهة React المبنية والمسارات `/api/v1` على نفس النطاق لتفادي اختلاف CORS بين المواقع.
- **Build command:** `npm run build:railway` (يشمل Prisma generate).
- **Start command:** `npm start`.
- **Pre-deploy command:** `npm run db:push` *فقط بعد مراجعة قاعدة البيانات والتأكد من أنها جديدة أو أخذ نسخة احتياطية؛ لا تستعمل `--accept-data-loss`*.
- حدّد `DATABASE_URL` برابط قاعدة PostgreSQL الداخلية في Railway، واضبط `JWT_SECRET` قويًا بطول 32 حرفًا على الأقل، و`WEB_ORIGIN` بالنطاق النهائي و`NODE_ENV=production`.
- بعد النشر المبدئي، لا يتم إنشاء حساب المالك أو تعبئة المنتجات تلقائيًا. نفّذ أمر seed بعناية لاحقًا ببيانات قوية وبعد اعتمادها.


## حسابات عملاء فهدان والبريد الإلكتروني

الواجهة: `/account/register` لإنشاء حساب؛ `/account/login` لتسجيل الدخول؛
`/account/forgot-password` لاستعادة كلمة المرور. رابط التفعيل والاستعادة يصل إلى بريد العميل
ولا يمنحه صلاحيات إدارية. روابط التفعيل صالحة 24 ساعة، وروابط الاستعادة 30 دقيقة.

### تفعيل إرسال البريد عبر Brevo

نعتمد Brevo لخدمة البريد الإلكتروني الخاص بإنشاء حسابات فهدان وتفعيلها واستعادة كلمة المرور.
أنشئ حسابًا في https://www.brevo.com ثم أضف نطاق إرسال تملكه إلى
Settings → Senders, Domains & Dedicated IPs → Domains، وأكمل توثيق DNS
وفق السجلات التي تعرضها Brevo (التحقق من الدومين وتوقيع DKIM وإعداد DMARC).
أنشئ عنوان مرسل Verified Sender من نفس النطاق، ثم أنشئ API Key من
SMTP & API → API Keys. أضف إلى متغيرات خدمة FAHDAN-OUD في Railway:

- `BREVO_API_KEY`: مفتاح Brevo API (سرّي، لخادم Node.js فقط).
- `BREVO_SENDER_EMAIL`: بريد مرسل موثّق في Brevo مثل `no-reply@your-verified-domain.example`.
- `BREVO_SENDER_NAME`: `فهدان للعود` (اختياري؛ اسم مرسل الرسالة).
- `WEB_ORIGIN`: الرابط النهائي للمتجر عبر HTTPS (موجود في Railway).

تستخدم الخوادم `POST https://api.brevo.com/v3/smtp/email` بوساطة ترويسة
`api-key` وترسل `sender` و`to` و`subject` و`htmlContent`.
لا تحتاج إلى مكتبة إضافية؛ يستعمل الخادم Node.js fetch.

لا تضع مفتاح API في GitHub أو كود React ولا تشارك قيمته في صور شاشة.
قبل ضبط مفتاح Brevo وعنوان المرسل يتعطل إنشاء الحساب واستعادة كلمة المرور
مع بقاء تصفح المتجر وتسجيل دخول الإدارة متاحين. مجرد توفير المتغيرات
لا يضمن التسليم قبل توثيق المرسل والتحقق من البريد الفعلي.
لا تُستخدم صلاحية Google Drive OAuth لإرسال البريد.

يُنشئ `prisma db push` جدول EmailActionToken ويضيف `User.emailVerifiedAt`
اختياريًا دون تعديل كلمات مرور الحسابات الحالية. سجّل حسابًا تجريبيًا من بريد تملكه،
واختبر وصول الرابط مرة واحدة، انتهاء صلاحيته، ثم استعادة كلمة المرور.

مهم قبل الإطلاق التجاري: إعداد Domain Authentication (SPF/DKIM/DMARC)
ومراقبة تسليم البريد، ووضع حماية إضافية من التسجيلات الآلية وتحديد معدل الإرسال.

## لوحة حساب العميل

- المسار `/account` متاح للعملاء المسجلين ذوي البريد الموثّق فقط.
- صفحة «نظرة عامة»: ملخص العناوين والطلبات وتاريخ الانضمام.
- «بياناتي الشخصية»: تحديث الاسم ورقم الهاتف. البريد معروض للقراءة فقط حتى تتوفر آلية تغيير موثّقة.
- «عناوين الشحن»: إضافة وتعديل وحذف حتى 10 عناوين وتعيين عنوان افتراضي. تُخزّن العناوين في PostgreSQL
  ضمن جدول `CustomerAddress` مرتبطة بمعرّف العميل؛ لا تُعرض لعملاء آخرين.
- «طلباتي»: تعرض آخر 50 طلبًا مرتبطًا بمعرّف العميل فقط مع حالة الطلب والأصناف والشحن؛ لا تعرض تكاليف الشراء
  أو أسعار الموردين. إتمام الشراء والدفع ليسا مفعلين حتى الآن.
- لا تقبل مسارات `/api/v1/account/*` إلا Customer JWT من نوع `purpose=customer`، مع تحقق إضافي
  من حالة الحساب وتوثيق البريد والدور وصلاحية الرمز في كل طلب.
- الحقل `CustomerAddress` إضافة مستقلة للمخطط. يجب فحص أثر `npm run db:push` بعناية قبل الإنتاج،
  وعدم استخدام `--accept-data-loss`.


### تحديد موقع التوصيل بالخريطة

عند إضافة أو تعديل عنوان الشحن يظهر محدد موقع تفاعلي باستخدام MapLibre GL وخرائط OpenFreeMap المتجهية المبنية على بيانات OpenStreetMap.
يمكن للعميل النقر على الخريطة، سحب الدبوس، أو استخدام موقع الجهاز بعد موافقته في المتصفح
(HTTPS). يُحفظ `latitude` و`longitude` ضمن `CustomerAddress` كحقول اختيارية؛
العناوين السابقة تظل صالحة دون موقع. رابط عرض الموقع يظهر لمالك العنوان فقط.

- لا تُطلب صلاحية تحديد الموقع تلقائيًا: يتطلب الأمر ضغط العميل على «موقعي الحالي».
- لا تُرسل إحداثيات العميل إلى مزود الخرائط لاستعلامات Geocoding؛ تُجلب بيانات وخطوط الخريطة
  من متصفح العميل عبر OpenFreeMap مع الإسناد الظاهر على الخريطة.
- يجب أن يراجع العميل اسم المدينة والحي والشارع يدويًا؛ الدبوس لا يملأها تلقائيًا.
- OpenFreeMap يسمح بالاستخدام التجاري ويقدم خدمة عامة مجانية دون ضمان SLA؛
  ينبغي اختيار مزود بمدد إتاحة مضمونة عند ازدياد أحجام التشغيل التجاري.
- تسمح Content Security Policy بتحميل أنماط وخطوط وبيانات OpenFreeMap فقط،
  وتشغيل MapLibre Worker من نفس نطاق المتجر، مع بقاء بقية خيارات Helmet محمية.
- تم إلغاء استخدام خادم الصور العام لـ OpenStreetMap بعد استجابته 403 Access blocked.


## عنوان التسليم الثابت للطلبات وتجهيز الشحن

يحتوي نموذج `Order` مسبقًا على `addressSnapshot: Json`. عند تطوير المعاملة الآمنة لإتمام
الشراء، **يجب** أن يختار العميل أحد عناوينه الموثقة، ثم يستدعي الخادم
`snapshotVerifiedCustomerDeliveryAddress(customerId,addressId)`
من `apps/api/src/lib/delivery.ts`، ويتحقق من وجود الإحداثيات وصحة ملكية العنوان.
تُحفظ **نسخة مستقلة غير مرتبطة لاحقًا بسجل العناوين** في `Order.addressSnapshot`
في نفس معاملة إنشاء الطلب والتحقق من المخزون والحجز/الدفع. لا يؤخذ السعر أو العنوان
المستخدم لإنشاء الطلب من بيانات غير موثوقة في المتصفح.

- `GET /api/v1/admin/orders`: عرض أحدث 100 طلب لمالك المتجر أو المدير فقط،
  بما يشمل وجهة التسليم المحفوظة ضمن الطلب وأرقام المستلمين. بيانات خاصة لا تُعرض علنًا.
- لوحة الإدارة: استعراض الطلبات، فتح موقع الشحنة في Google Maps بإحداثيات رقمية،
  نسخ رابط الملاحة أو بيانات التسليم يدويًا. لا توجد مشاركة تلقائية لشركات الشحن.
- `GET /api/v1/account/orders`: يرجع الموقع المحفوظ ضمن الطلب إلى صاحبه وحده.
- الطلبات القديمة التي لا تتضمن إحداثيات تُعرض مع تنبيه؛ لا يتم التخمين
  أو استبدال عنوان الطلب بعنوان العميل الحالي.
- نظام الدفع وإنشاء الطلبات والحجز وإصدار بوليصات الشحن وتكامل شركات التوصيل
  لم يُفعَّل بعد. هذه خطوة تأسيسية للطلب والشحن، وليست نظام شحن تجاري مكتملًا.
- تتضمن روابط Google Maps الإحداثيات عند فتحها، لذا ينبغي مشاركتها فقط مع
  شركة الشحن المخوّلة لأغراض التوصيل وفق سياسة الخصوصية والاحتفاظ بالبيانات.


## الإتمام المبدئي للطلب (Checkout — بدون دفع)

- تفتح السلة صفحة `/checkout` للعملاء المسجّلين فقط.
- يطلب الخادم `POST /api/v1/checkout/quote` ويعيد تسعير الأصناف من قاعدة البيانات،
  ويرفض المنتجات التجريبية وغير النشطة والكميات غير المتوفرة.
- يختار العميل عنوانه المحفوظ وإحداثياته، ثم يوافق صراحةً على إرسال
  **طلب مبدئي غير مدفوع وغير محجوز المخزون**.
- `POST /api/v1/checkout/request`: يعيد التحقق من العنوان وملكيته ومن الدبوس
  ومن الأسعار والأرصدة، ثم يحفظ الطلب وحركة أصنافه مع نسخة ثابتة من الموقع.
  الحالة الجديدة `AWAITING_REVIEW`. رقم الطلب الفريد الموجود أصلًا في PostgreSQL
  يُشتق من معرّف المحاولة وحساب العميل، ويمنع تكرار الطلب عند إعادة المحاولة.
- **لا يتم الدفع أو الحجز أو الشحن** بهذه العملية. لم تُعتمد أجرة الشحن أو
  المعالجة الضريبية بعد؛ المبلغ المعروض هو مجموع المنتجات المبدئي فقط،
  ولا يُعامل `shippingSar=0` و`taxSar=0` داخليًا كتسعير نهائي.
- تظهر الطلبات في «طلباتي» وفي إدارة الطلبات، مع حالة «بانتظار مراجعة المتجر».
- هذا إجراء تمهيدي يُمكّن فريق المتجر من مراجعة الطلب والاتصال بالعميل.
  لا تفعّل التحصيل والشحن تلقائيًا قبل إعداد سياسات الشحن والضريبة والدفع
  ومعاملات حجز/صرف المخزون.


## تسجيل أول صنف فعلي ومخزونه (لوحة المدير)

من صفحة `/admin` افتح «إدخال المنتجات والمشتريات الفعلية»، وسجّل:
رمزًا فريدًا للصنف واسم المنتج ونوعه والمنشأ والدرجة، ثم اسم المورد وتاريخ الاستلام
والكمية الحقيقية والتكلفة الإجمالية شاملة أي مصاريف شراء مخصصة للصنف وحد إعادة الطلب،
ثم أدخل حجم بيع واحدًا على الأقل وسعره الحقيقي.

**لا تُقدَّر الأسعار أو الأرصدة تلقائيًا.** ينشئ السيرفر بعملية قاعدة بيانات واحدة:
`Product` بحالة `DRAFT`، و`ProductVariant` لكل حجم، و`Supplier` عند الحاجة،
و`Purchase` و`PurchaseLine`، و`InventoryLot` بتكلفة وحدة داخلية،
و`InventoryBalance` و`StockMovement` من نوع `PURCHASE_RECEIPT`.
جميع بيانات المورد وتكلفة الشراء لا تُعرض في واجهة المتجر العامة.

بعد حفظ المسودة، استخدم «مكتبة صور المنتجات — Google Drive» لرفع صورة حقيقية
للصنف. ثم اختر «نشر المنتج» من قائمة المنتجات في لوحة المدير.
لا يسمح الخادم بالنشر دون صورة مخزنة ورصيد فعلي وحجم بيع مسعّر يمكن توفيره.
المنتج بحالة `DRAFT` لا يظهر للعملاء ولا يمكن تقديم طلب شراء له.
يمكن إيقاف النشر والعودة إلى `DRAFT` عند الحاجة دون حذف سجلات المخزون.

عند العودة إلى واجهة المتجر تُحدَّث التشكيلة. اختبر إضافة حجم حقيقي إلى السلة،
ثم اختر «مراجعة الطلب المبدئي». يلزم تسجيل دخول عميل مؤكد البريد وعنوان شحن
بإحداثيات موثقة. لا تُحصّل الأموال ولا تُحجز الكميات في هذه المرحلة.

**حدود التنفيذ:** هذه شاشة إنشاء منتج واستلام أول دفعة شراء، وليست نظام إدارة
كاملًا لتعديل الدفعات اللاحقة أو تصحيح المخزون أو إلغاء فواتير شراء. هذه العمليات
تحتاج سجلات محاسبية وتصحيحية منفصلة، ولا يصح تعديل رصيد المخزون يدويًا دون حركة.


## رفع صور متعددة للمنتج

من لوحة الإدارة، بعد حفظ المنتج الجديد اضغط «رفع صور المنتج»، أو افتح
«مكتبة صور المنتجات — Google Drive». اختر المنتج ثم حدد عدة ملفات دفعة واحدة
بالضغط على زر اختيار الملفات (`multiple`)، مع إمكانية إضافة المزيد للانتظار
وحذف الصور غير المطلوبة قبل رفعها. تظهر معاينة مصغرة لكل ملف وعداد الرفع.
تُرسل الملفات واحدًا تلو الآخر عبر المسار الحالي `POST /api/v1/admin/products/:productId/images`
ولا يحتاج النظام إلى مفاتيح Google إضافية.

- أقصى عدد محفوظ: **12 صورة** لكل منتج؛ حد حجم الملف الواحد **6 MiB**.
- الأنواع المدعومة: JPEG وPNG وWebP، مع فحص ترويسة الملف على الخادم.
- يحتفظ الخادم بترتيب الصور في `ProductMedia.sort`، وتظهر الأولى صورة أساسية
  في بطاقة المنتج، ويمكن للعميل التنقل بينها من المصغرات في صفحة المنتج.
- يسمح الخادم بالرفع للمدير المخول فقط؛ وتظل صور المسودات غير متاحة لواجهة
  العملاء حتى نشر المنتج.
- في حالة تعطل رفع بعض الصور تبقى الملفات التي فشل رفعها وحدها محددة لإعادة المحاولة.
- تظل صور Google Drive غير عامة، وتُعرض للعميل من مسار الصور الداخلي للمنتجات المنشورة.


## حفظ المنتج والصور في خطوة واحدة

في `/admin` داخل «إدخال المنتجات والمشتريات الفعلية»، أصبح القسم الرابع
«صور المنتج — Google Drive» يسمح باختيار **حتى 12 صورة** قبل الضغط على زر
«حفظ المنتج ورفع الصور». الصيغ المدعومة JPEG وPNG وWebP؛ 6 MiB حد أقصى للصورة.

تسلسل العمل: ينشئ الخادم المنتج كمسودة ويثبت الاستلام وسجل المخزون
والتكلفة أولًا، ثم يرسل المتصفح الصور المختارة واحدة تلو الأخرى إلى
`POST /api/v1/admin/products/:productId/images` بنفس صلاحية الإدارة المعتادة.
الصورة الأولى هي الغلاف. لا يُنشر المنتج تلقائيًا.

**ملاحظة عن الفشل الجزئي:** قد ينجح تسجيل المنتج ولا ينجح رفع صورة أو أكثر.
عندها يحتفظ النموذج بمعرّف المنتج والملفات الفاشلة فقط؛ يمكن إعادة رفعها
دون تكرار إنشاء المنتج أو دفعة الاستلام. ويمكن متابعة إدخال منتج آخر،
وإضافة الصور المتبقية لاحقًا عبر «مكتبة صور المنتجات — Google Drive».
بعد تحديث الصفحة يفقد المتصفح الملفات المحلية غير المرفوعة، لكن المنتج
والصور الناجحة المحفوظة تبقى في PostgreSQL وDrive.

تبقى المكتبة المنفصلة لإضافة المزيد من الصور إلى المنتجات السابقة
دون إدخال المنتج مرة أخرى. لا تتطلب هذه الميزة أي تعديل لجداول PostgreSQL.


## مراجعة المنتجات واعتماد النشر من المدير

تبدأ المنتجات الفعلية الجديدة بحالة `DRAFT`، وتظهر للمدير ضمن قسم
«مراجعة واعتماد المنتجات قبل عرضها للعملاء» أعلى لوحة `/admin`،
ولا تُعرض هذه المنتجات عبر `GET /api/v1/products` أو
`GET /api/v1/products/:slug` أو مسار الصور العام.
في نسخة الإنتاج لا تعود الواجهة إلى منتجات تجريبية عند تعطل API.

من قسم المراجعة يستطيع المدير مشاهدة الأصناف غير المعتمدة، الصور المرفوعة
(عبر مسار خاص يتطلب جلسة الإدارة)، بيانات المنشأ والوصف، المورد وبيانات الشراء
الداخلية، رصيد المخزون، أحجام البيع وأسعارها. يمكن تصحيح بيانات العرض
والأسعار للمنتج وهو `DRAFT` فقط. لا تسمح هذه الشاشة بتعديل كميات
المخزون أو تكاليف الشراء المحاسبية.

يتطلب اعتماد النشر ثلاث إقرارات مراجعة صريحة للبيانات والصور والأسعار،
إضافةً إلى صورة واحدة على الأقل ورصيد متاح وحجم سعره صالح.
`PATCH /api/v1/admin/products/:id/publishing` يرفض حالة `ACTIVE`
ما لم يُرسل `confirmed:true` من جلسة مدير موثقة.
يُسجَّل الاعتماد وإيقاف النشر والتصحيحات في `AuditLog` مع حساب المدير،
ويظل المنتج مخفيًا عن العملاء حتى نجاح العملية داخل PostgreSQL.
يتيح القسم إيقاف النشر وإعادة المنتج إلى `DRAFT` قبل تعديل بياناته أو
إعادة اعتماده. لا تتطلب هذه الآلية إضافة أعمدة أو تغييرات للمخزون.


## إدارة المنتج بعد اعتماده

من قسم «مراجعة واعتماد المنتجات» في `/admin`، تتوفر الآن إدارة الصور
والمخزون للأصناف المسجلة:

- **صور المنتج:** تغيير الغلاف، وتقديم/تأخير الصور، وحذف صورة، بحد أقصى
  12 صورة في المنتج، مع حفظ ترتيب `ProductMedia.sort`.
  لا يسمح الخادم بتغيير الصور لمنتج `ACTIVE`؛ يجب أولًا إيقاف نشره وإعادته
  إلى `DRAFT`، ثم مراجعة التعديلات واعتماده مجددًا. وينطبق الأمر نفسه على
  تغيير الوصف والأسعار. لا تظهر المسودات في واجهة العملاء.
- **استلام شراء جديد:** إدخال المورد والكمية والتكلفة الفعلية وتاريخ الاستلام
  ومرجع الفاتورة. يُنشئ الخادم ضمن معاملة واحدة شراءً، وسطر شراء،
  ودفعة مخزون ذات تكلفة وحدة، وحركة `PURCHASE_RECEIPT`، ويزيد الرصيد.
- **نقص مخزون موثق:** التلف، والفقد، وتصحيح النقص الفعلي في الجرد.
  يتطلب سببًا لا يقل عن 8 أحرف، ولا يسمح بخصم أكثر من الرصيد المتاح
  بعد استبعاد الحجوزات. تُخصم الكمية من دفعات المخزون الأقدم أولًا،
  مع تسجيل حركة لكل دفعة وتكلفتها.
- **المراقبة:** تعرض لوحة الإدارة الرصيد الفعلي، والمحجوز، والمتاح،
  وآخر 25 حركة مستودعية، مع حفظ هوية منفذ العملية في `AuditLog`.
- **السلامة والتكرار:** تستعمل العمليات معاملات PostgreSQL من مستوى
  Serializable وتحديثًا مشروطًا لإصدار الرصيد، ومفاتيح UUID فريدة
  لحركات المستودع لمنع المعالجة المكررة.
- **الخصوصية:** تكلفة الشراء والمورد والحركات والصور غير المنشورة لا تُعرض
  للعملاء. صورة الحذف تُزال أولًا من سجل العرض ثم تُحذف من Drive؛
  إذا فشل تنظيف Drive تظهر رسالة لإتمام المراجعة يدويًا.

**قيد مهم:** الزيادة غير المرتبطة بمستند شراء أو تصحيح جرد موجب غير متاحة
حاليًا؛ يجب استخدام استلام شراء موثق، أو تطوير إجراء محاسبي مستقل للتسويات
الموجبة. لا تُعدَّل كميات المخزون أو تكاليف الدفعات مباشرةً دون حركة.


## طلبات الاستبدال والاسترجاع ومستندات الشراء

تظهر سياسة «الاستبدال والاسترجاع واسترداد الأموال» عبر المسار العام
`/returns-policy` والتذييل. يراجع فريق المتجر طلبات العملاء من لوحة الإدارة.

**العميل:** من «حسابي ← الاستبدال والاسترجاع» يستطيع اختيار منتج من
طلب تم تسليمه، واختيار استرجاع أو استبدال، وتحديد الكمية والسبب ووصف
الواقعة، وتوضيح ما إذا استُخدمت العبوة. لا يسمح الخادم بطلب كمية
أكبر من المشتراة بعد احتساب الطلبات الأخرى غير المرفوضة.
حق العدول الاعتيادي (CHANGED_MIND) يخضع لمهلة 7 أيام من تاريخ التسليم
الموثق، وإذا لم يوجد تاريخ تسليم مسجل تُحال الحالة للمراجعة اليدوية.
العيب والتلف وعدم المطابقة لا تُرفض آليًا بانتهاء المهلة. الطلبات قبل
التسليم تُراجع مع خدمة المتجر بإجراء إلغاء منفصل.

**المدير:** من `/admin` قسم «طلبات الاستبدال والاسترجاع»،
يمكن طلب معلومات إضافية، أو الموافقة، أو الرفض بتسبيب، وبعد الموافقة
توثيق وصول المرتجع. التغيرات المسجلة في `AuditLog`. لا يتم تسجيل
عملية رد أموال أو إعادة السلعة للمخزون تلقائيًا من هذه الميزة؛ يلزم فحص
مادي ومستند تسوية منفصل، ثم تنفيذ رد الدفع عبر بوابة دفع معتمدة.

**المستندات:** كل طلب له مستند خاص بصاحبه عند
`/account/orders/:id/document`، ويمكن طباعته أو حفظه PDF من المتصفح.
للطلبات `AWAITING_REVIEW` يظهر **«مستند طلب مبدئي غير مدفوع»**
مع إجمالي منتجات غير نهائي، دون نسب ضريبة أو رسوم شحن مختلقة.
إذا كان هناك دفع `CAPTURED` يغطي مبلغ الطلب بالفعل، تصبح النسخة
«إيصال شراء غير ضريبي»؛ وهي ليست فاتورة إلكترونية ضريبية ولا تتضمن
رقم فاتورة/QR ضريبي مُصطنعًا. يجب تنفيذ مسار فوترة ZATCA بمعرف ضريبي
وإعدادات تاجر معتمدة وXML/QR والمتطلبات الفنية قبل إصدار الفاتورة
الضريبية القانونية. لا تتعامل مع مستند الطباعة باعتباره بديلًا عنها.

**الأمان:** كل مستند واسترجاع يتطلب تحقق JWT خاصًا بمالك حساب العميل.
مسار إدارة طلبات الاسترجاع محمي بحساب OWNER/ADMIN فقط. تُستخدم
كميات ومدفوعات وطلبات حقيقية من PostgreSQL، دون نشر بيانات المورد
أو تكلفة الشراء للعميل.

**مراجع نظامية:** نظام التجارة الإلكترونية — وزارة التجارة،
والفوترة الإلكترونية «فاتورة» — هيئة الزكاة والضريبة والجمارك.
