# فهدان للعود | FAHDAN OUD

**الإصدار 0.1.0 — الهيكل البرمجي الأساسي**

مشروع متجر إلكتروني عربي بـ **React + TypeScript + Vite** للواجهة، و**Node.js + Express + TypeScript** للـ API، و**PostgreSQL + Prisma** للبيانات. يحتفظ بالهوية المعتمدة: أخضر داكن `#172721`، ذهبي `#BA9764`، خلفية عاجية `#F7F4EE`.

> **ليس متجرًا جاهزًا لاستقبال الطلبات**: الدفع والشحن وإنشاء الطلبات محجوبة عمدًا. الأمثلة والأسعار التوضيحية ليست منتجات حقيقية. يجب أن تُعتمد معلومات التواصل وقصة العلامة والسياسات قبل النشر.

## معاينة فورية دون تشغيل الخادم

افتح الملف `preview/index.html` في المتصفح لمراجعة الشكل المبدئي المعتمد. هذه نسخة HTML توضيحية مستقلة؛ النظام الجديد يعمل عبر `apps/web` و `apps/api`.

## 1. المتطلبات

- Node.js **20.19+** (يُفضّل الإصدار 22 LTS).
- npm، وPostgreSQL 16 (مباشرة أو عبر Docker Desktop).
- اتصال بالإنترنت لتنزيل حزم npm أول مرة.

## 2. التشغيل المحلي — Windows PowerShell

```powershell
# من داخل مجلد fahdan-oud-app
npm install
Copy-Item apps/api/.env.example apps/api/.env
# افتح apps/api/.env وعدّل JWT_SECRET و ADMIN_EMAIL و ADMIN_PASSWORD
# استخدام Docker Desktop لتشغيل قاعدة البيانات المحلية:
docker compose up -d
npm run db:generate
npm run db:push
npm run db:seed
npm run dev
```

- واجهة المتجر: **http://localhost:5173**
- API: **http://localhost:4000/api/v1/health**
- دخول المالك: **http://localhost:5173/admin** (بعد تعيين بياناته في `.env` وتشغيل `db:seed`).
- إن أردت رؤية منتجات وهمية من قاعدة البيانات نفسها: غيّر `SEED_DEMO=true` مؤقتًا في `apps/api/.env` وأعد تشغيل `npm run db:seed`، ثم ارجعه إلى `false`. لا تُستخدم هذه الخطوة في الإنتاج.

**إن لم تكن لديك Docker:** وفّر قاعدة PostgreSQL مستقلة وعدّل `DATABASE_URL` ثم تابع `db:generate` و `db:push` و `db:seed` و `dev`.

**توليد سر JWT من PowerShell:**

```powershell
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

ضع الناتج في `JWT_SECRET` بدل القيمة التوضيحية. اختر كلمة مرور فريدة بطول 16 رمزًا على الأقل لحساب المالك. لا ترفع `.env` إلى أي مستودع Git.

## 4. قواعد المخزون

- كل صنف عود يملك رصيدًا في **وحدته الأساسية بالجرام**. المتغيرات (10، 20، 28، 36، 50، 100، 125، 250، 500، 1000) ليست مخزونًا مستقلاً.
- العطور قد تستخدم **ملليلتر**، والبكجات **قطعة**. لا يُفرض الجرام على جميع أنواع المنتجات.
- المتاح = الكمية الفعلية - المحجوزة. لا يتم تقليل مخزون على أساس تجربة السلة.
- تكلفة الشراء، المورد، وحدات تكلفة الدفعات وCOGS موجودة في نماذج خاصة بالخلفية، ولا تصل لواجهة العميل.
- في الإنتاج، البيع الحقيقي يحتاج معاملات ذرية وحجزًا مع انتهاء صلاحية وتأكيدًا للدفع قبل الخصم النهائي.

## 5. حالة التحقق

- أُنشئت ملفات المصدر والبنية التقنية وقيم التجربة.
- لم يُجرَ `npm install` أو build كامل داخل بيئة الإنشاء بسبب عدم إمكانية الوصول إلى registry.npmjs.org؛ يلزم التثبيت واختبار التشغيل في جهاز يتصل بالإنترنت.
- راجع `docs/ROADMAP.md` لما أُنجز وللخطوات التالية، و`docs/SECURITY-NOTES.md` لما يلزم قبل التشغيل التجاري.

## 6. النشر لاحقًا

يمكن فصل `apps/web` و`apps/api` إلى خدمات مع PostgreSQL، وربطهما باستضافة تدعم Node وPostgreSQL مثل Railway عند طلب النشر. يجب ضبط `WEB_ORIGIN` و`VITE_API_BASE` وأسرار الإنتاج، وتشغيل `prisma migrate deploy` بعد إعداد migrations، وعدم نشر أي معلومات وهمية على أنها بضائع للبيع.

## 7. نشر موحّد في Railway

- خادم Express يستضيف واجهة React المبنية والمسارات `/api/v1` على نفس النطاق لتفادي اختلاف CORS بين المواقع.
- **Build command:** `npm run build:railway` (يشمل Prisma generate).
- **Start command:** `npm start`.
- **Pre-deploy command:** `npm run db:push` *فقط بعد مراجعة قاعدة البيانات والتأكد من أنها جديدة أو أخذ نسخة احتياطية؛ لا تستعمل `--accept-data-loss`*.
- حدّد `DATABASE_URL` برابط قاعدة PostgreSQL الداخلية في Railway، واضبط `JWT_SECRET` قويًا بطول 32 حرفًا على الأقل، و`WEB_ORIGIN` بالنطاق النهائي و`NODE_ENV=production`.
- بعد النشر المبدئي، لا يتم إنشاء حساب المالك أو تعبئة المنتجات تلقائيًا. نفّذ أمر seed بعناية لاحقًا ببيانات قوية وبعد اعتمادها.


## حسابات عملاء فهدان والبريد الإلكتروني

الواجهة: `/account/register` لإنشاء حساب؛ `/account/login` لتسجيل الدخول؛
`/account/forgot-password` لاستعادة كلمة المرور. رابط التفعيل والاستعادة يصل إلى بريد العميل
ولا يمنحه صلاحيات إدارية. روابط التفعيل صالحة 24 ساعة، وروابط الاستعادة 30 دقيقة.

### تفعيل إرسال البريد عبر Brevo

نعتمد Brevo لخدمة البريد الإلكتروني الخاص بإنشاء حسابات فهدان وتفعيلها واستعادة كلمة المرور.
أنشئ حسابًا في https://www.brevo.com ثم أضف نطاق إرسال تملكه إلى
Settings → Senders, Domains & Dedicated IPs → Domains، وأكمل توثيق DNS
وفق السجلات التي تعرضها Brevo (التحقق من الدومين وتوقيع DKIM وإعداد DMARC).
أنشئ عنوان مرسل Verified Sender من نفس النطاق، ثم أنشئ API Key من
SMTP & API → API Keys. أضف إلى متغيرات خدمة FAHDAN-OUD في Railway:

- `BREVO_API_KEY`: مفتاح Brevo API (سرّي، لخادم Node.js فقط).
- `BREVO_SENDER_EMAIL`: بريد مرسل موثّق في Brevo مثل `no-reply@your-verified-domain.example`.
- `BREVO_SENDER_NAME`: `فهدان للعود` (اختياري؛ اسم مرسل الرسالة).
- `WEB_ORIGIN`: الرابط النهائي للمتجر عبر HTTPS (موجود في Railway).

تستخدم الخوادم `POST https://api.brevo.com/v3/smtp/email` بوساطة ترويسة
`api-key` وترسل `sender` و`to` و`subject` و`htmlContent`.
لا تحتاج إلى مكتبة إضافية؛ يستعمل الخادم Node.js fetch.

لا تضع مفتاح API في GitHub أو كود React ولا تشارك قيمته في صور شاشة.
قبل ضبط مفتاح Brevo وعنوان المرسل يتعطل إنشاء الحساب واستعادة كلمة المرور
مع بقاء تصفح المتجر وتسجيل دخول الإدارة متاحين. مجرد توفير المتغيرات
لا يضمن التسليم قبل توثيق المرسل والتحقق من البريد الفعلي.
لا تُستخدم صلاحية Google Drive OAuth لإرسال البريد.

يُنشئ `prisma db push` جدول EmailActionToken ويضيف `User.emailVerifiedAt`
اختياريًا دون تعديل كلمات مرور الحسابات الحالية. سجّل حسابًا تجريبيًا من بريد تملكه،
واختبر وصول الرابط مرة واحدة، انتهاء صلاحيته، ثم استعادة كلمة المرور.

مهم قبل الإطلاق التجاري: إعداد Domain Authentication (SPF/DKIM/DMARC)
ومراقبة تسليم البريد، ووضع حماية إضافية من التسجيلات الآلية وتحديد معدل الإرسال.

## لوحة حساب العميل

- المسار `/account` متاح للعملاء المسجلين ذوي البريد الموثّق فقط.
- صفحة «نظرة عامة»: ملخص العناوين والطلبات وتاريخ الانضمام.
- «بياناتي الشخصية»: تحديث الاسم ورقم الهاتف. البريد معروض للقراءة فقط حتى تتوفر آلية تغيير موثّقة.
- «عناوين الشحن»: إضافة وتعديل وحذف حتى 10 عناوين وتعيين عنوان افتراضي. تُخزّن العناوين في PostgreSQL
  ضمن جدول `CustomerAddress` مرتبطة بمعرّف العميل؛ لا تُعرض لعملاء آخرين.
- «طلباتي»: تعرض آخر 50 طلبًا مرتبطًا بمعرّف العميل فقط مع حالة الطلب والأصناف والشحن؛ لا تعرض تكاليف الشراء
  أو أسعار الموردين. إتمام الشراء والدفع ليسا مفعلين حتى الآن.
- لا تقبل مسارات `/api/v1/account/*` إلا Customer JWT من نوع `purpose=customer`، مع تحقق إضافي
  من حالة الحساب وتوثيق البريد والدور وصلاحية الرمز في كل طلب.
- الحقل `CustomerAddress` إضافة مستقلة للمخطط. يجب فحص أثر `npm run db:push` بعناية قبل الإنتاج،
  وعدم استخدام `--accept-data-loss`.
