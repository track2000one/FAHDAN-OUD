# الهيكل التقني والتشغيلي المقترح — فهدان للعود

## حدود هذا التسليم
المرفق `index.html` نموذج واجهات تفاعلي محلي فقط، وليس متجرًا منشورًا أو متصلًا بقاعدة بيانات أو بوابة دفع. جميع الأسعار والأصناف والمخزون والإيرادات أمثلة اختبارية. المخطط `prisma/schema.prisma` نقطة انطلاق لبناء خدمة الخلفية، لم تُشغّل له ترحيلات قاعدة بيانات بعد.

## التقنية
- المتجر ولوحة الإدارة: React + Vite + TypeScript، واجهات RTL، مع استهداف دعم العربية والإنجليزية لاحقًا.
- API: Node.js + Express + TypeScript، مع Zod للتحقق من المدخلات وجلسات آمنة/رموز وصول، وRBAC للصلاحيات.
- قاعدة البيانات: PostgreSQL + Prisma. حقول الأسعار والكميات من نوع Decimal؛ تجنب `float` في النقد.
- تخزين الملفات: مخزن كائنات خاص/عام مضبوط الصلاحيات للصور والفيديو؛ قاعدة البيانات تخزن المسارات والبيانات التعريفية، لا الوسائط الثنائية الكبيرة.
- النشر الممكن: GitHub مع CI وإدارة إصدارات؛ Railway للـAPI وقاعدة البيانات واستضافة الواجهة في خدمة مناسبة. **لم يُنشأ مستودع ولم يُجرَ نشر في هذه المرحلة.**
- المراقبة: أخطاء الخادم، صحة الخدمات، نسخ احتياطية مشفرة مع اختبار استعادة دوري، وتدقيق لكل تعديل مالي أو مخزني.

## الصفحات الأساسية
**واجهة العميل**: الرئيسية؛ الأقسام؛ نتائج البحث والفلترة؛ صفحة المنتج متعددة الأحجام؛ السلة؛ إتمام الشراء؛ صفحة نجاح الدفع؛ تتبع الطلب؛ حساب العميل؛ من نحن؛ الشحن والاسترجاع؛ الخصوصية؛ التواصل.

**الإدارة**: نظرة عامة؛ المنتجات ووسائطها؛ درجات العود ومواصفاته؛ الأسعار وأحجام البيع؛ الموردون والمشتريات والدفعات؛ المخزون وحركاته والعينات؛ الطلبات والمدفوعات والإرجاعات؛ العملاء والمديونية؛ الشحن والتغليف؛ المصروفات؛ التقارير والصلاحيات وسجل التدقيق؛ إعدادات المتجر.

## المنتج الواحد والأحجام
- هوية واحدة للصنف `Product` تتضمن: البلد والمنطقة ودرجة العود وطبيعي/مسقّى وطابع الرائحة والفوحان والثبات والاستخدامات والصور وفيديو التبخير.
- لكل وزن **SKU مستقل بالسعر** تحت الصنف نفسه `ProductVariant` مثل 10/20/28/36/50/100/125/250/500/1000 جم؛ ولا يُنشأ مخزون وهمي منفصل لكل وزن.
- تعريف الأوقية في المتجر **28 جم تجاريًا** بموجب قرار صاحب المتجر، وليس تحويل الأونصة العلمية (28.3495 جم). الثمن = 125 جم وفق تعريفك للمنتج.
- يمكن أن تكون وحدة أساس الأصناف الأخرى `MILLILITER` لدهن العود و`PIECE` للبكجات، ولا يُجبر كل صنف على الجرام.
- الإتاحة لكل SKU: `الكمية المتاحة من المنتج بوحدة الأساس >= كمية SKU × عدد الوحدات المطلوبة` مع تطبيق قاعدة الحجز الذرّي.
- الأسعار تحفظ على مستوى المتغير `ProductVariant` مستقلة؛ الخصومات المعلنة تُحسب على الخادم مع تاريخ صلاحية، مقارنةً بسعر أساس حقيقي موثق. أسعار النموذج فقط تعتمد خصمًا حسابيًا تجريبيًا للأحجام الكبيرة.

## معادلات المخزون والأرباح

`المخزون الفعلي = مجموع الكميات المستلمة - المشحونة/المباعة - العينات - الفاقد + المرتجعات المعاد قبولها + التسويات الموقعة`

`المتاح للبيع = المخزون الفعلي - المحجوز مؤقتًا لطلبات قيد الدفع`

`تكلفة الجرام الفعلية = (سعر شراء الدفعة + المصروفات المرتبطة بشرائها والقابلة للرسملة) ÷ صافي جراماتها المستلمة`

`إجمالي الربح لكل منتج = صافي إيراد المنتج دون ضريبة محصلة لصالح الهيئة - تكلفة الوحدات المباعة`

`صافي الربح = إجمالي الربح - المصاريف التشغيلية - رسوم بوابة الدفع - صافي الشحن الذي يتحمله المتجر - أثر المرتجعات والخسائر الأخرى` مع مراعاة المعالجة المحاسبية الصحيحة لضريبة القيمة المضافة بحسب التسجيل الضريبي.

**لا تُعد المبيعات غير المسددة نقدًا محصلًا**. يفصل النظام بين حالة الطلب، وحالة الدفع، والمديونية، والتدفق النقدي. كذلك يميز رأس المال الممول من المالك عن تكلفة المشتريات، فلا يجمعهما على أنهما مصروف واحد.

## سيناريو شراء متزامن دون بيع زائد
1. يختار العميل `SKU = 125g` ويطلب دفعًا.
2. تبدأ معاملة قاعدة بيانات مع قفل الصف المناسب أو تحديث ذرّي مشروط على الرصيد: لا يقبل الحجز إلا إذا `onHand - reserved >= 125g`.
3. يخزن `StockReservation` بمهلة زمنية واضحة وينشأ Order مبدئي.
4. يحدث العميل الدفع في بوابة دفع مرخّصة؛ تؤكد الـAPI العملية **من إشعار خادم موقّع ومتحقق منه** وليس من إعادة التوجيه وحدها، مع معرّف idempotency ثابت.
5. عند السداد، ينتقل الطلب إلى مؤكد؛ عند التجهيز والشحن تُسجل حركة صرف مخزون بإجمالي كمية SKU ويُرفع الحجز المقابل؛ عند فشل الدفع أو انقضاء المهلة يُفك الحجز.
6. عند الإرجاع لا يعود المخزون إلى المتاح تلقائيًا؛ يُفحص المنتج وتحدد صلاحيته للبيع وتسجل حركة إرجاع ومرجع مالي.

## الأمن والخصوصية
- صلاحيات: OWNER وADMIN وINVENTORY_MANAGER وSALES وACCOUNTANT وCUSTOMER. واجهة العميل وAPI العام **لا يعرضان تكلفة الشراء أو المورد أو صافي الربح**.
- التحقق من الصلاحية يُطبّق على الخادم وليس إخفاء عناصر واجهة فقط؛ سجّل كل وصول وتعديل حساس.
- حماية تسجيل الدخول بـ MFA للإدارة، ضبط المحاولات، جلسات آمنة، تهيئة CORS وCSRF حسب أسلوب الجلسات، وتشفير أثناء النقل.
- تخزين أسرار قاعدة البيانات والدفع في البيئة الآمنة وعدم وضعها في GitHub أو الواجهة.
- معالجة دفع مستضافة أو عناصر واجهة آمنة لتجنب تخزين بيانات البطاقات وحماية بيانات العملاء، مع سياسات الاحتفاظ والموافقة.

## واجهات API الرئيسية (تصميم مبدئي)
- `GET /api/catalog/products`, `GET /api/catalog/products/:slug`
- `POST /api/orders/checkout`, `GET /api/orders/:id`
- `POST /api/payments/webhook` (مع تحقق من التوقيع وازدواجية الإشعارات)
- `GET/POST/PATCH /api/admin/products`, `GET/POST /api/admin/purchases`
- `POST /api/admin/inventory/adjustments`, `GET /api/admin/reports/profit`
- `GET /api/admin/receivables`, `POST /api/admin/expenses`

## متطلبات السعودية — تحقق قبل الإطلاق
- توثيق المتجر وفق الضوابط المعتمدة في منصة الأعمال وبيانات المنشأة والحساب البنكي التجاري.
- صفحة الشروط وسياسات الشحن والاستبدال والاسترجاع والخصوصية وقنوات الشكاوى والإفصاح عن بيانات المتجر.
- تطبيق VAT والفوترة الإلكترونية بحسب حالة المنشأة والتزاماتها؛ ربط المرحلة الثانية عند انطباق اشتراطاتها، وليس الادعاء بأن نموذج الفاتورة التجريبي متوافق.
- ربط بوابة مرخصة ومدى/Visa/Mastercard/Apple Pay بعد إبرام العلاقة واجتياز موافقتها؛ تابي/تمارا اختياري لاحقًا. الشحن مربوط بمزود فعلي في مرحلة التكامل.
- قبل اعتماد وصف المنتج، راجع دقة بلد المنشأ ومكوناته وتصريحاته ومتطلبات الوسم/التراخيص الخاصة بنوع السلعة عند انطباقها.
